API для фронта VPNHub

Типы лежат в packages/shared/src (types.ts - кабинет, admin.ts - админка, articles.ts - разделы).
Как должна вести себя каждая ручка, видно по мокам: apps/miniapp/src/api/mock.ts и apps/admin/src/api/mock/.
Если пути или поля у вас другие, правится apps/*/src/api/index.ts.


ОБЩЕЕ

Базовый адрес берётся из VITE_API_URL, например https://api.example.com/api.
JSON, поля в snake_case как в database.dbml. Деньги - число в рублях, скидки - доля от 0 до 1.
Даты в ISO 8601 с поясом.

Ошибка - любой не-2xx с телом {"detail": "текст"} или {"message": "текст"}, текст показывается пользователю.
Список ошибок валидации FastAPI тоже понимаем, показываем первую.
401 - токен протух (на сайте выкидывает на вход, в телеге просит переоткрыть), 403 - нет прав, 404 - не найдено.
Пустой ответ - 204.

Таймаут 30 секунд. GET при обрыве или 5xx повторяется один раз, POST/PUT/PATCH/DELETE не повторяются никогда.
Пустой ответ там, где ждём данные, считается ошибкой (кроме GET /subscription, там null = подписки нет).

CORS нужен только если API на другом домене: origin кабинета и админки, методы GET POST PUT PATCH DELETE,
заголовки Authorization и Content-Type. Куки не используем.


АВТОРИЗАЦИЯ

В телеге каждый запрос идёт с заголовком Authorization: tma <initData>.
Бэк проверяет подпись токеном бота и свежесть auth_date, юзера берёт из поля user, нового регистрирует.
https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app

На сайте вход через Telegram Login Widget: POST /auth/telegram с данными виджета
(id, first_name, username, photo_url, auth_date, hash и ref, если пришёл по реф. ссылке).
Бэк проверяет hash, при первом входе регистрирует (ref - код ref_links или id пригласившего) и отдаёт {"token": "..."}.
Дальше запросы с Authorization: Bearer <token>. На 401 просим войти заново.
https://core.telegram.org/widgets/login#checking-authorization
Домен сайта надо привязать к боту: @BotFather -> /setdomain.

Без авторизации фронт ходит только в POST /auth/telegram и GET /settings (на входе по реф. ссылке показываем бонус).


КАБИНЕТ

POST /auth/telegram - вход с сайта, ответ {token}
GET /me - юзер и баланс
PUT /me/email {email} - привязать почту, занята или кривая -> 422 с detail. Поля email в users пока нет, надо добавить
GET /subscription - подписка, нет подписки -> 404 (или пустой ответ, или status NOT_FOUND)
GET /tariffs - цены, скидки за устройства, общая и персональная скидка
GET /payment-methods - только включённые, по sequence_number
GET /settings - ссылка на поддержку и размеры реф. бонусов
GET /articles - включённые разделы «Информация» и «Помощь» по sequence_number (подробнее ниже)
POST /invoices {provider, amount} - счёт с pay_url
GET /invoices/:id - счёт
GET /invoices?status=UNPAID - неоплаченные счета юзера, новые сверху
POST /subscription/purchase {days, devices} - покупка/продление, ответ подписка
POST /subscription/slots {count} - докупить пустые слоты к активной подписке
PUT /subscription/auto-renewal {is_enabled, days}
POST /subscription/slots/:id/release - отвязать устройство, слот остаётся, 204
DELETE /subscription/slots/:id - удалить слот, 204

Пополнение. POST /invoices создаёт счёт, нужен pay_url. Если провайдер даёт ссылку не сразу - pay_url: null,
фронт напишет «Готовим ссылку» и будет ждать её в GET /invoices/:id. Пока окно счёта открыто, опрашиваем раз в 3 сек.
После PAID обновляем баланс. Неоплаченные счета обновляются раз в 10 сек, пока список не пуст.
Истёкшие счета бэк сам переводит в EXPIRED. Чтобы счета не копились: если есть UNPAID на ту же сумму
тем же провайдером - вернуть его, и ограничить число неоплаченных (например 5, сверху 429 или 422 с detail).
amount не меньше min_amount у способа оплаты и не больше 1 000 000.
/topup?amount=300 открывает пополнение с подставленной суммой.

Цена. Фронт считает по формуле из packages/shared/src/pricing.ts:
тариф * устройства * дни * (1 - скидка за устройства) * (1 - max(персональная, общая)).
Тариф - цена дня на срок, между точками prices по прямой (1 дн. 5 р, 30 дн. 4 р -> 15 дн. 4,52 р).
Итог считает бэк и списывает с баланса, не хватает -> ошибка с detail.

Продление заранее - тот же POST /subscription/purchase, devices = текущее число слотов.
Бэк прибавляет дни к expires_at, слоты и автопродление не трогает.

Истёкшая подписка: GET /subscription отдаёт status DISABLED, slots остаются.
Кабинет показывает возобновление, devices не меньше числа слотов, покупка тем же purchase,
устройства должны сохраниться. DELETE /subscription/slots/:id должен работать и при DISABLED, последний слот удалить нельзя.

Докупка слотов: count - сколько добавить (до 1000 всего), срок не меняется.
Цена: остаток срока в днях дробью * тариф на этот остаток * новые слоты, со скидкой за устройства после покупки.
Формула slotsQuote в pricing.ts.

purchases.kind для статистики: первая покупка VPN_FIRST_PURCHASE, на активную подписку VPN_EXTENSION,
после окончания VPN_RENEWAL, автопродление VPN_AUTORENEWAL.
В Subscription.slots только неудалённые слоты.


РАЗДЕЛЫ «ИНФОРМАЦИЯ» И «ПОМОЩЬ»

Кабинет: GET /articles - включённые разделы.
Админка:
GET /admin/articles - все, включая скрытые
POST /admin/articles - создать, sequence_number ставить в конец своего kind
PATCH /admin/articles/:id - изменить любые поля
DELETE /admin/articles/:id - удалить, 204
PUT /admin/articles/order {kind, ids} - новый порядок (ids сверху вниз), ответ все разделы

Поля: id, kind (INFO или HELP), slug, emoji, title, lead, body, sequence_number, is_active.
Если таблица с разделами уже есть - можно отдавать её, поля при необходимости поправить в api/index.ts.
Если нет - примерно так:

  articles
    id serial pk
    kind varchar - INFO / HELP
    slug varchar(64) - адрес /info/<slug>, уникален внутри kind
    emoji text - имя эмодзи из паков (VHubProject_17), custom_emoji_id или обычный символ
    title varchar(120)
    lead varchar(255) null - описание
    body text - HTML как в телеге
    sequence_number int
    is_active bool default true
    created_at, updated_at

Проверки: title не пустой, slug из латиницы, цифр и дефиса и уникален внутри kind, иначе 422 с detail.
body хранить как есть, чистить не нужно - фронт сам показывает только безопасные теги.
Начальные тексты - DEFAULT_ARTICLES в packages/shared/src/articles.ts.
Пока GET /articles отдаёт 404, кабинет показывает их.

Кастомные эмодзи <tg-emoji emoji-id="..."> показываются анимацией, если ID есть в packages/shared/src/customEmojiIds.ts,
иначе символом внутри тега. Список ID обновляет apps/miniapp/scripts/emoji-ids.mjs.
Блок «Не нашли ответ?» не редактируется, ссылка в нём - support_link из настроек.


АДМИНКА

Все пути с /admin. Пускать OWNER, ADMIN и SUPPORT_AGENT, для USER - 403.
SUPPORT_AGENT только смотрит пользователей: GET /admin/me, GET /admin/users*, GET /admin/invoices?user_id=...
На всё остальное и на любые изменения ему 403.

GET /admin/me - id, tg_user_id, role
GET /admin/dashboard?tz=... - сводка для главной
GET /admin/users - список, плюс фильтры role и flag
GET /admin/users/:id - карточка
GET /admin/users/:id/referrals - список рефералов
GET /admin/users/:id/ledger?page=&page_size= - история баланса, новые сверху
POST /admin/users/:id/balance {direction, amount, comment} - начислить/списать
GET /admin/invoices - список, плюс status, provider, user_id, from, to, date_by
GET /admin/payment-methods - все, включая выключенные
PATCH /admin/payment-methods/:id {name, is_active, min_amount}
GET /admin/settings
PATCH /admin/settings {support_link, invited_bonus, referral_bonus}
GET /admin/stats/range
GET /admin/stats/users
GET /admin/stats/deposits
GET /admin/stats/purchases
(+ ручки разделов выше)

Списки: page (с 1), page_size (до 100), sort, order (asc/desc), q - поиск.
Ответ {items, total, page, page_size}, total - сколько всего под фильтром.
Пользователи: q по id, tg_user_id (точно) и language_code; sort по id, tg_user_id, registered_at, balance,
subscription_expires_at, referrals_count. flag: bot, blocked, premium, trial, active_sub. Пустые значения в конце.
Рефералы: sort по id, invited_at, deposits_total.
Счета: q по id, user_id, tg_user_id (точно) и external_invoice_id (вхождение); sort по id, amount, created_at, paid_at.
from/to - ISO с поясом, [from, to), любую границу можно не передавать. date_by=created (по умолчанию) или paid.
Зависшие счета на главной - это status=UNPAID&to=<сейчас минус час>, отдельной ручки не надо.

Баланс: direction IN - начисление (ADMIN_ADD), OUT - списание (ADMIN_DEDUCT). amount > 0,
списать больше баланса нельзя (422). comment пишем в audit_logs. Ответ - карточка юзера.

Статистика: from, to (to не включается), granularity (hour, day, month, year), tz (например Europe/Moscow).
Интервалы считать в поясе tz, t - начало интервала, отдавать все интервалы подряд, пустые нулями.
Фронт берёт весь период один раз и пересчитывает сам, для hour - только последние 31 день.

Пользователи: дату блокировки и пометки «бот» не храним, поэтому по времени считаются только регистрации,
а категории - по текущим флагам. Боты - все is_bot, заблокировали - не боты с is_blocked_bot, активные - остальные.
now - {total, blocked, bots} на сейчас, в точках total (накопительно), new_total, new_blocked, new_bots.

Пополнения: оплаченные счета по paid_at, суммы в рублях как зачислены (ledger DEPOSIT).
total_before - сумма до from. В точке amount, count и то же по провайдерам в by_provider.

Покупки: по created_at, в by_kind количество и сумма по purchases.kind, slots - сколько слотов куплено.

Сводка: «сегодня» и «за 30 дней» в поясе tz, daily - последние 30 дней,
latest_users и latest_invoices - по 6 последних. Обновляется раз в минуту.
